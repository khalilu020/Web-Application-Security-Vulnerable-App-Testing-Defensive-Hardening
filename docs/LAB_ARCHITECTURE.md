## Design Decision: Co-located Target and Wazuh Manager

**What was done:** DVWA (the intentionally vulnerable target) and the Wazuh manager/dashboard were deployed on the **same Debian VM**, rather than on separate hosts.

**Why this is not the recommended production pattern:**

In a real deployment, the system being monitored (the target) and the system performing monitoring/detection (the SIEM) should always be on separate hosts. The reasoning:

1. **Blast radius.** If a vulnerability on the target is successfully exploited to gain code execution, an attacker who compromises the target should *not* simultaneously gain a foothold on the security team's detection infrastructure.
2. **Log integrity.** A monitored host with local admin/root compromise could, in principle, tamper with or stop the very logs and services meant to detect it.
3. **Realistic architecture.** Recruiters and reviewers with security backgrounds will (correctly) flag "target and SIEM manager on the same box" as an anti-pattern if presented without context.

**Why it was done anyway, for this lab:**

Given local hardware constraints (single physical machine, limited VM headroom), co-locating the target and the Wazuh manager was the pragmatic choice that let this project fit inside the available lab environment without requiring a third VM. It does not materially affect the validity of the exploitation, remediation, or detection-rule work — all vulnerabilities were exploited and detected exactly as they would be in a properly segmented environment.

**Evidence the trade-off is real, not just theoretical:** During Local File Inclusion (LFI) testing (see Assessment Report, Finding 7), reading `/etc/passwd` on the target incidentally revealed the presence and naming convention of the Wazuh service accounts (`wazuh`, `wazuh-indexer`, `wazuh-dashboard`) and Wazuh's install path (`/var/ossec`). In a properly segmented deployment, an LFI vulnerability on the target application would never expose *any* information about the SIEM, because the SIEM would not be reachable from the target at all. This is a direct, observed consequence of the co-location decision and is documented as its own note in the assessment report.

**What would be done differently with more resources:** A three-host layout — attacker (Kali), target (DVWA on a minimal host), and SIEM manager (Wazuh on a separate host) — with the target running a lightweight Wazuh *agent* (not the manager) forwarding logs to the remote manager. This is the standard production pattern and the one referenced throughout the detection engineering section of the report.

## Independent Confirmation: CIS Benchmark Scan

Wazuh's built-in Security Configuration Assessment (SCA) module ran a CIS Debian Linux 12 Benchmark scan against the target host, independent of any manual testing performed in this project. It scored **37/100** (117 of 207 checks failed), including an explicit failed check: *"Ensure web server services are not in use"* — a direct, automated, third-party confirmation of the same architectural concern raised above. This is included as corroborating evidence rather than a finding of this assessment, since it was generated by Wazuh's own compliance tooling rather than through manual testing.

## Attacker Host Note

The attacker machine (Kali Linux) is run natively on physical hardware rather than as a VM. This is a valid and common configuration for practitioners who use Kali as their primary security workstation. It does not affect the validity of any finding — all testing was performed over the network against the target VM's IP address, identically to how it would be performed from a virtualized attacker host.
